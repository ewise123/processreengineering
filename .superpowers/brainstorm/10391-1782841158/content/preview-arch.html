How should the non-committal ghost preview render?

The planner already turns a bundle into an ordered MutationStep[]. Today the executor runs those steps against the live API. For a preview we need to show the result without saving, then have Apply run the real thing and Cancel drop the ghosts. Two architectures:

A

Overlay layer — keep the real graph, paint ghosts on top

The live canvas stays exactly as-is. The planner's steps drive a separate, purely-visual overlay: ghost boxes for create_node, dashed ghost lines for create_edge, strike markers on objects slated for delete/reroute, a small "→ new name" tag floating by a relabel. No graph data is mutated.

Pros

  • Real graph never touched — zero risk to live state
  • Cheap for adds/deletes/connects (the common suggest cases)

Cons

  • Relabel / move-to-lane / rename-lane are awkward — you're tagging an unchanged node rather than showing it changed
  • Two code paths to keep in sync (overlay rendering vs. real rendering)
B

Shadow graph — render an in-memory "after" graph, style the diff

Apply the plan to an in-memory copy of the graph (no API), and render the canvas from that shadow while in preview mode. Diff shadow-vs-real to style each delta: new nodes/edges ghosted, relabeled nodes show the new name with a ghost ring, deletions struck through, moved nodes sit in their new lane. Apply then runs the same plan for real; Cancel throws the shadow away.

Pros

  • Uniform — all 12 op kinds preview the same way, including relabel/move/rename
  • One render path; preview = "render from shadow + diff styling"
  • Reuses the planner's geometry decisions, so preview matches the real result

Cons

  • Needs an in-memory plan-executor (a pure version of the canvas executor) + a graph differ
  • More upfront machinery than the overlay

My lean: B (shadow graph). The reason is exactly your earlier point — the preview has to be honest about all changes (a relabel or a lane-move must look changed, not just tagged), and B handles every op kind through one path. It also gives us the in-memory executor we can later reuse to compute deletion impact (orphans, bridges) on the same shadow. A costs less now but fights us on the edit-type ops and on deletion-impact analysis.
